# 보안 기본 개념

## 한 줄 요약

정보보안은 허가된 사용자가 허가된 정보와 기능에 적절하게 접근할 수 있도록 보호하는 활동이다.

보안은 단순히 정보를 숨기는 것만 의미하지 않는다. 정보가 **함부로 노출되지 않고, 함부로 변경되지 않으며, 필요할 때 정상적으로 사용할 수 있는 상태**를 유지하는 것이 핵심이다.

---

## CIA 3요소

정보보안의 가장 기본적인 목표는 **기밀성(Confidentiality), 무결성(Integrity), 가용성(Availability)**이며, 이를 묶어 CIA Triad라고 한다.

### 기밀성 (Confidentiality)

허가되지 않은 사용자가 정보를 보지 못하도록 보호하는 성질이다.

쉽게 말하면 **"봐도 되는 사람만 보게 하는 것"**이다.

왜 중요한가?

정보는 단순한 데이터가 아니라 계정 권한, 개인정보, 돈, 회사 자산 등과 연결될 수 있다. 비밀번호가 노출되면 계정 탈취로 이어질 수 있고, 고객 정보가 유출되면 사칭이나 피싱 같은 2차 피해가 발생할 수 있다.

즉,

`기밀성 실패 → 정보 유출 → 유출된 정보를 이용한 2차 공격 → 실제 피해`

대표적인 보호 수단:
- 암호화
- 접근통제
- 인증
- 권한관리
- VPN

대표적인 침해 사례:
- 패킷을 몰래 가로채어 내용을 열람
- 고객 DB 유출
- 권한 없는 사용자의 내부 문서 열람

시험 포인트:

**비인가자가 정보를 열람하면 기밀성 침해**이다.

---

### 무결성 (Integrity)

정보가 허가 없이 변경되거나 훼손되지 않았음을 보장하는 성질이다.

쉽게 말하면 **"데이터를 함부로 건드리지 못하게 하고, 바뀌었다면 알아낼 수 있게 하는 것"**이다.

예를 들어 은행 DB의 잔액이 `100,000원`에서 `10,000,000원`으로 임의 변경되었다면 무결성이 침해된 것이다. 사용자 입장에서 이득처럼 보여도 시스템 관점에서는 장부 데이터의 신뢰성이 깨진 심각한 문제다.

대표적인 침해 사례:
- DB 값 임의 수정
- 파일 내용 변조
- 로그 삭제 또는 조작
- 송금 금액 변조
- 프로그램 코드 변경

대표적인 보호 수단:
- 해시
- MAC(Message Authentication Code)
- 전자서명
- 접근통제
- 변경 이력 관리

#### 해시와 무결성

파일의 해시값을 미리 저장해두고 나중에 다시 계산했을 때 값이 달라지면 내용이 변경되었다는 사실을 알 수 있다.

즉, 해시는 주로 **변조 여부를 탐지**하는 데 사용된다.

시험 포인트:

**비인가자가 데이터를 수정하거나 삭제하면 무결성 침해**이다.

---

### 가용성 (Availability)

필요한 사용자가 필요할 때 시스템이나 정보를 사용할 수 있도록 보장하는 성질이다.

쉽게 말하면 **"써야 할 때 서비스가 죽어 있지 않게 하는 것"**이다.

대표적인 침해 또는 원인:
- DoS / DDoS
- 서버 장애
- 네트워크 단절
- 디스크 장애
- 자원 고갈
- 랜섬웨어로 시스템 사용 불가

대표적인 보호 수단:
- 이중화
- 백업
- Failover
- 로드밸런싱
- DDoS 방어
- 모니터링

#### 일반 장애와 보안 사고의 차이

결과만 보면 둘 다 서비스가 중단될 수 있지만, 원인이 다르다.

- 서버 고장이나 설정 실수로 서비스 중단 → 일반 장애
- 공격자가 DDoS나 랜섬웨어 등으로 서비스를 중단 → 보안 사고

가용성이 보안 요소에 포함되는 이유는 공격자가 데이터를 훔치거나 변조하지 않더라도 **서비스 자체를 사용하지 못하게 만드는 것**을 공격 목표로 삼을 수 있기 때문이다.

시험 포인트:

**서비스를 정상적으로 사용할 수 없게 되면 가용성 침해**로 볼 수 있다.

---

## CIA 한 번에 기억하기

- 기밀성: 못 보게
- 무결성: 못 바꾸게
- 가용성: 못 죽게

## 추가적인 보안 속성

CIA 외에도 실제 보안에서는 인증성, 추적가능성, 부인방지 등의 속성이 중요하다.

### 인증성 (Authentication / Authenticity)

사용자 또는 데이터가 주장하는 대상이 실제로 맞는지 확인하는 성질이다.

쉽게 말하면 **"너 진짜 누구야?"**를 확인하는 것이다.

예:
- ID/PW 로그인
- OTP
- 인증서
- 전자서명을 통한 송신자 확인

---

### 추적가능성 (Accountability)

누가 언제 어떤 행동을 했는지 나중에 확인할 수 있도록 하는 성질이다.

예:

`02:13 / adminA / 방화벽 정책 변경`

이런 기록이 남아 있으면 사고가 발생했을 때 행위자를 추적할 수 있다.

추적가능성을 보장하는 대표적인 수단이 **감사로그(Audit Log)**이다.

---

### 부인방지 (Non-repudiation)

사용자가 자신이 수행한 행위를 나중에 부인하지 못하도록 증거를 남기는 성질이다.

쉽게 말하면 **"해놓고 안 했다고 하지 못하게 하는 것"**이다.

전자서명이 대표적인 수단이다.

---

## 인증과 인가

### 인증 (Authentication)

사용자가 누구인지 확인하는 과정이다.

예: ID/PW, OTP, 인증서

### 인가 (Authorization)

인증된 사용자가 특정 자원이나 기능을 사용할 권한이 있는지 확인하는 과정이다.

정리:
- 인증 = 너 누구야?
- 인가 = 너 이거 해도 돼?

---

## 감사로그 (Audit Log)

감사로그는 **누가, 언제, 무엇을 했는지 기록하는 로그**이다.

일반 로그가 시스템에서 어떤 일이 발생했는지 확인하는 데 초점이 있다면, 감사로그는 사용자나 관리자의 **행위 추적**에 초점이 있다.

대표적인 기록 대상:
- 로그인 및 로그아웃
- 계정 생성 및 삭제
- 권한 변경
- 관리자 기능 실행
- 파일 삭제
- DB 또는 시스템 설정 변경

### 감사로그의 주요 용도

1. 사고 발생 시 행위자 추적
2. 보안 감사
3. 침해사고 조사
4. 변경 이력 확인
5. 부인방지 지원

### 장애 분석에도 사용할 수 있는가?

가능하다. 다만 감사로그의 1차 목적은 장애 로그가 아니라 **행위 추적**이다.

예:

`10:02 adminA가 방화벽 정책 변경`

`10:05 서비스 통신 실패 시작`

이 경우 감사로그를 통해 장애 직전 어떤 관리 작업이 있었는지 확인할 수 있으므로 장애 원인 분석에 큰 도움이 된다.

반대로 CPU 폭주, 메모리 부족, 애플리케이션 예외, DB Timeout 같은 문제는 시스템 로그, 애플리케이션 로그, 모니터링 지표를 확인하는 것이 더 적절하다.

정리:

- 감사로그 = 누가 무엇을 했는가
- 시스템/애플리케이션 로그 = 시스템에서 무엇이 일어났는가

## 보안 문제를 보는 기본 흐름

보안 개념은 다음 흐름으로 보면 이해하기 쉽다.

`자산 → 위협 → 취약점 → 공격 → 침해 → 보안 대책`

### 자산 / 위협 / 취약점 / 위험 / 공격

- **자산(Asset)**: 보호해야 하는 대상. 예: 서버, DB, 개인정보, 계정, 소스코드
- **취약점(Vulnerability)**: 자산이 가진 약점. 예: 약한 비밀번호, 미패치 서버, 입력값 검증 부족
- **위협(Threat)**: 취약점을 이용해 피해를 줄 수 있는 요인. 예: 공격자, 악성코드, 내부자, 화재, 장비 고장
- **위험(Risk)**: 위협이 취약점을 이용해 실제 피해를 일으킬 가능성과 그 영향
- **공격(Attack)**: 실제로 취약점을 악용하는 행위

예:

- 자산: 고객 DB
- 취약점: SQL 입력값 검증 부족
- 위협: 외부 공격자
- 위험: 고객정보 유출 가능성과 그 피해 규모
- 공격: 악성 SQL 구문 입력

위험은 흔히 **발생 가능성(Likelihood) × 영향도(Impact)** 개념으로 이해한다.

## 위험관리 (Risk Management)

위험관리는 **위험을 찾아서, 얼마나 큰지 평가하고, 어떻게 처리할지 정하는 과정**이다.

기본 흐름:

`위험 식별 → 위험 평가 → 위험 대응 → 모니터링`

### 위험 대응 4가지

- **회피(Avoid)**: 위험한 일을 아예 하지 않음
- **감소/완화(Mitigate)**: 보안대책을 적용해 위험을 낮춤
- **전가/이전(Transfer)**: 위험 부담을 보험이나 외부 전문업체 등에 넘김
- **수용(Accept)**: 위험이 작거나 대응 비용이 더 크면 감수함

쉽게 기억하기:

- 회피 = 안 한다
- 감소 = 줄인다
- 전가 = 넘긴다
- 수용 = 감수한다

핵심은 **위험을 0으로 만드는 것이 아니라 허용 가능한 수준까지 낮추는 것**이다.

## 접근통제 (Access Control)

접근통제는 **누가 어떤 자원에 어디까지 접근할 수 있는지 제한하는 것**이다.

### 식별 / 인증 / 인가

- **식별(Identification)**: 사용자가 자신이 누구인지 주장하는 단계
- **인증(Authentication)**: 그 사용자가 실제로 맞는지 확인하는 단계
- **인가(Authorization)**: 인증된 사용자가 무엇을 할 수 있는지 결정하는 단계

정리:

- 식별 = "나는 누구다"
- 인증 = "진짜 맞아?"
- 인가 = "그럼 어디까지 해도 돼?"

### 최소 권한 원칙 (Principle of Least Privilege)

사용자에게 업무 수행에 필요한 **최소한의 권한만 부여**하는 원칙이다.

예:

로그 조회만 필요한 사용자에게 DB 삭제 권한까지 줄 필요는 없다.

### Need-to-Know

업무상 알아야 하는 정보에만 접근할 수 있도록 제한하는 원칙이다.

예:

같은 회사 직원이어도 인사팀 급여정보를 모든 직원이 볼 필요는 없다.

### 대표적인 접근통제 모델

#### DAC (Discretionary Access Control)

- Discretionary = 재량에 따른
- 자원 **소유자가 자신의 재량으로 권한을 결정**
- 쉽게 기억: **주인이 결정**

#### MAC (Mandatory Access Control)

- Mandatory = 의무적인, 강제적인
- 개인이 아니라 **시스템이나 보안정책이 강제로 권한을 결정**
- 쉽게 기억: **정책이 결정**

#### RBAC (Role-Based Access Control)

- Role-Based = 역할 기반
- 사용자 개인이 아니라 **역할(Role)에 권한을 부여**
- 쉽게 기억: **역할이 결정**

예:

- 개발자 역할 → 로그 조회 가능
- DBA 역할 → DB 변경 가능
- 인사팀 역할 → 급여정보 조회 가능

## 인증 요소와 MFA

인증 수단은 **사용자가 본인임을 무엇으로 증명하느냐**에 따라 구분한다.

### 지식 기반 (Something you know)

내가 **알고 있는 것**으로 인증한다.

예:
- 비밀번호
- PIN
- 보안질문

### 소유 기반 (Something you have)

내가 **가지고 있는 것**으로 인증한다.

예:
- 휴대폰
- OTP 토큰
- 스마트카드
- 보안토큰

### 생체 기반 (Something you are)

내 **신체적 특징**으로 인증한다.

예:
- 지문
- 얼굴
- 홍채
- 정맥

### 왜 나누는가?

서로 다른 종류의 인증요소를 조합하면 하나가 탈취되어도 다른 요소가 추가로 막아줄 수 있기 때문이다.

예:

`비밀번호 + 휴대폰 OTP = 지식 + 소유`

공격자가 비밀번호를 알아내더라도 휴대폰까지 확보해야 하므로 공격 난도가 높아진다.

### MFA (Multi-Factor Authentication)

**서로 다른 인증요소를 2개 이상 조합**하는 방식이다.

중요한 점은 단순히 인증수단을 두 개 쓰는 것이 아니라 **서로 다른 Factor를 사용해야 한다는 것**이다.

예:

- 비밀번호 + PIN → 둘 다 지식 기반 → 서로 다른 Factor 2개가 아님
- 비밀번호 + OTP → 지식 + 소유 → 2FA 가능
- OTP + 지문 → 소유 + 생체 → 2FA 가능

### 외우기

- Know = 아는 것
- Have = 가진 것
- Are = 나 자체

---

## 시험 포인트 요약

- 기밀성: 정보의 비인가 열람 방지
- 무결성: 정보의 비인가 변경 및 훼손 방지
- 가용성: 정상적인 서비스 이용 보장
- 인증성: 사용자나 데이터의 진위 확인
- 추적가능성: 누가 어떤 행위를 했는지 확인 가능
- 부인방지: 자신의 행위를 나중에 부인하지 못하게 함
- 감사로그: 사용자 및 관리자의 행위 추적
- 위험 대응: 회피 / 감소 / 전가 / 수용
- 식별 / 인증 / 인가를 구분할 것
- DAC = Discretionary, 소유자 재량
- MAC = Mandatory, 정책에 의한 강제
- RBAC = Role-Based, 역할 기반
- MFA는 서로 다른 인증요소 조합인지 확인할 것
- MAC은 문맥에 따라 MAC Address와 Message Authentication Code가 다르므로 주의

## 실무 연결

서비스 장애나 DDoS는 단순 운영 문제뿐 아니라 가용성 침해로도 볼 수 있다. 모니터링과 장애 대응은 보안의 가용성 측면과 연결되며, 감사로그는 장애 직전의 관리자 작업이나 설정 변경을 확인할 때도 유용하다.
