# HTTPS, TLS, 인증서 체인과 핸드셰이크

## 1. HTTPS 전체 흐름

웹 브라우저에서 `https://example.com` 같은 주소에 접속하면 바로 HTTP 데이터를 주고받는 것이 아니다.

큰 흐름은 다음과 같다.

```text
DNS
→ TCP 3-Way Handshake
→ TLS Handshake
→ 암호화된 HTTP 통신
```

HTTPS는 다음처럼 이해하면 된다.

```text
HTTPS = HTTP over TLS
```

즉 HTTP 데이터를 TLS로 암호화해서 주고받는 방식이다.

---

## 2. TCP 3-Way Handshake

TCP는 연결지향형 프로토콜이기 때문에 실제 데이터를 보내기 전에 서로 통신 가능한 상태인지 먼저 확인한다.

```text
클라이언트                서버

   SYN
----------------------->

            SYN + ACK
<-----------------------

   ACK
----------------------->
```

쉽게 말하면 다음과 같다.

```text
SYN      : "나 너랑 연결하고 싶어."
SYN+ACK  : "네 요청 받았고, 나도 준비됐어."
ACK      : "좋아. 네 응답도 받았어."
```

핵심 순서:

```text
SYN → SYN/ACK → ACK
```

전화 통화 전에 `여보세요? → 네, 들려요 → 저도 들려요` 하고 확인하는 것과 비슷하다.

---

## 3. TLS Handshake란?

Handshake는 영어로 실제로 `악수`라는 뜻이다.

TLS Handshake는 본격적인 암호화 통신을 시작하기 전에 클라이언트와 서버가 서로 조건을 맞추는 과정이다.

핵심 목적은 다음과 같다.

1. 어떤 TLS 버전과 암호 방식을 사용할지 정한다.
2. 서버가 진짜인지 인증서를 통해 확인한다.
3. 이후 통신에 사용할 공통 세션키를 만든다.

전체 흐름을 단순화하면 다음과 같다.

```text
ClientHello
→ ServerHello
→ 서버 인증서 전달
→ 인증서 검증
→ 키 교환
→ 세션키 생성
→ Finished
```

중요한 점은 `TLS Handshake`가 끝났다고 TLS 자체가 끝나는 것은 아니라는 것이다.

```text
TLS Handshake
= TLS 연결을 만드는 준비 과정

TLS
= Handshake + 이후 암호화된 데이터 통신 전체
```

---

## 4. ClientHello와 ServerHello

### ClientHello

클라이언트가 먼저 서버에게 자신이 지원하는 TLS 버전, 암호 알고리즘 등의 정보를 보낸다.

쉽게 말하면:

```text
"나는 이런 TLS 버전과 암호 방식을 지원해."
```

### ServerHello

서버는 클라이언트가 제시한 조건 중 사용할 것을 선택해 응답한다.

```text
"좋아. 그럼 이 방식으로 통신하자."
```

---

## 5. 서버 인증서

TLS Handshake 도중 서버는 자신의 인증서를 클라이언트에게 전달한다.

인증서는 쉽게 말하면 다음과 같다.

> 이 공개키가 실제로 이 서버의 공개키라는 것을 증명하는 전자 신분증

인증서에는 보통 다음 정보가 들어간다.

- 인증서 대상
- 서버의 공개키
- 유효기간
- 발급자
- CA의 전자서명

서버가 단순히 `나 example.com이고 이게 내 공개키야`라고 말하는 것만으로는 믿을 수 없다.

공격자도 같은 말을 할 수 있기 때문이다.

그래서 인증서 체인을 확인한다.

---

## 6. 인증서 체인

인증서 체인은 다음 질문을 위로 따라가는 구조다.

> 이 서버 인증서를 누가 보증했고, 그 기관은 또 누가 보증했는가?

일반적인 구조:

```text
서버 인증서
→ 중간 CA
→ 루트 CA
```

브라우저는 아래에서 위로 전자서명을 검증한다.

```text
서버 인증서
→ 중간 CA의 공개키로 서명 검증

중간 CA 인증서
→ 루트 CA의 공개키로 서명 검증

루트 CA
→ 브라우저/OS Trust Store에 있는지 확인
```

최종적으로 신뢰 가능한 루트 CA에 도달하면 인증서 체인을 신뢰할 수 있다고 판단한다.

### 루트 CA는 왜 믿는가?

루트 CA 인증서는 보통 Self-Signed, 즉 자기 자신이 서명한 인증서다.

하지만 자기서명이라서 믿는 것이 아니다.

브라우저나 운영체제의 `Trust Store`에 미리 신뢰 대상으로 등록되어 있기 때문에 믿는 것이다.

따라서 최종 신뢰 기준은 다음과 같다.

```text
브라우저 / OS의 Trust Store
```

---

## 7. 중간 CA 인증서가 변조되면?

중간 CA 인증서에는 루트 CA의 전자서명이 붙어 있다.

공격자가 중간 CA 인증서 내용을 변경하면 인증서 내용의 해시값도 바뀌기 때문에 기존 루트 CA 서명과 맞지 않게 된다.

```text
정상 중간 CA 인증서
→ 루트 CA의 서명과 일치

변조된 중간 CA 인증서
→ 루트 CA의 서명과 불일치
→ 검증 실패
```

즉 단순한 인증서 파일 변조는 전자서명 검증 단계에서 탐지할 수 있다.

하지만 `중간 CA의 개인키 자체`가 탈취되면 훨씬 위험하다.

공격자가 진짜 중간 CA처럼 새로운 인증서에 서명할 수 있기 때문이다.

이 경우 해당 중간 CA 인증서를 폐기하고 더 이상 신뢰하지 않도록 처리해야 한다.

---

## 8. 인증서 검증에서 확인하는 것

브라우저는 인증서 체인만 확인하는 것이 아니다.

주로 다음을 함께 확인한다.

- 인증서 체인이 신뢰 가능한 루트 CA까지 이어지는가
- 현재 접속한 도메인과 인증서의 도메인이 일치하는가
- 인증서 유효기간이 정상인가
- 인증서가 폐기된 상태가 아닌가

폐기 상태 확인에는 CRL이나 OCSP 같은 방식이 사용될 수 있다.

---

## 9. 세션키와 대칭키 암호

서버 인증이 끝나면 클라이언트와 서버는 실제 HTTP 데이터를 암호화하기 위한 세션키를 준비한다.

실제 HTTPS 데이터를 비대칭키 암호로 계속 암호화하지 않는 이유는 계산 비용이 크고 느리기 때문이다.

따라서 구조는 다음과 같다.

```text
초기 연결 / 인증 / 키 합의
→ 비대칭키 기반 기술 사용

실제 데이터 통신
→ 빠른 대칭키 암호 사용
```

즉 TLS Handshake 과정에서 세션키를 준비하고, 이후 HTTP 요청과 응답은 그 세션키를 사용한 대칭키 방식으로 암호화한다.

---

## 10. Diffie-Hellman의 핵심 아이디어

Diffie-Hellman은 다음 문제를 해결한다.

> 비밀키 자체를 네트워크로 보내지 않고도 두 사람이 같은 비밀값을 만들 수 없을까?

핵심 아이디어는 다음과 같다.

```text
공개값 + 내 비밀값
→ 중간값 생성
→ 중간값만 서로 교환

상대의 중간값 + 내 비밀값
→ 둘이 같은 최종 비밀값 계산
```

비밀값 자체는 네트워크로 보내지 않는다.

쉽게 말하면:

> 키를 보내는 것이 아니라, 같은 키를 각자 계산해서 만든다.

Diffie-Hellman 자체는 상대방의 신원을 인증하지 못하기 때문에 단독으로 사용하면 MITM 공격 문제가 생길 수 있다.

TLS에서는 인증서/전자서명을 이용해 서버 신원을 확인하고, 별도의 키 합의 방식으로 공통 비밀값을 만든다.

---

## 11. ECDH와 ECDHE

현대 TLS에서는 전통적인 DH보다 타원곡선을 이용한 방식이 널리 사용된다.

- `DH`: Diffie-Hellman 기본 방식
- `ECDH`: Elliptic Curve Diffie-Hellman
- `ECDHE`: ECDH + Ephemeral

`Ephemeral`은 일회성, 임시라는 뜻이다.

ECDHE는 연결마다 새로운 임시 키 쌍을 사용한다.

이 때문에 나중에 서버의 장기 개인키가 유출되더라도 과거에 캡처된 통신까지 한꺼번에 복호화하기 어렵다.

이 성질을 `Forward Secrecy`, 순방향 비밀성이라고 한다.

중요한 구분:

```text
서버 인증서의 공개키
→ 서버가 진짜인지 인증 / 서명 검증에 사용

ECDHE의 임시 키
→ 클라이언트와 서버가 공통 비밀값을 합의하는 데 사용
```

즉 서버 인증서의 공개키가 곧 세션키를 만드는 키라는 뜻은 아니다.

## 12. HTTPS 전체 과정 다시 보기

```text
사용자가 https://example.com 접속

        ↓

DNS
도메인의 IP 주소 확인

        ↓

TCP 3-Way Handshake
SYN → SYN/ACK → ACK

        ↓

TLS Handshake

ClientHello
↓
ServerHello
↓
서버 인증서 전달
↓
서버 인증서 → 중간 CA → 루트 CA 검증
↓
서버 신원 확인
↓
ECDHE 등의 방식으로 키 합의
↓
공통 비밀값에서 세션키 생성
↓
Finished

        ↓

TLS 연결 완료

        ↓

HTTP 요청/응답을
세션키를 이용해 암호화하여 전송
```

## 13. 핵심 요약

### TCP 3-Way Handshake

```text
SYN → SYN/ACK → ACK
```

목적:

> TCP 연결을 만든다.

### TLS Handshake

목적:

```text
서버 인증
+ 암호 방식 협상
+ 세션키 준비
```

### 인증서 체인

```text
서버 인증서
→ 중간 CA
→ 루트 CA
→ Trust Store
```

목적:

> 서버가 제시한 공개키가 진짜 그 서버의 것인지 확인한다.

### Diffie-Hellman / ECDHE

목적:

> 비밀값을 직접 보내지 않고 클라이언트와 서버가 같은 공통 비밀값을 만든다.

### HTTPS

```text
HTTPS = HTTP over TLS
```

전체를 한 문장으로 정리하면 다음과 같다.

> 서버를 찾고 TCP 연결을 맺은 뒤, TLS Handshake에서 서버의 인증서를 검증하고 공통 세션키를 준비한 다음, 그 세션키로 HTTP 요청과 응답을 암호화해서 주고받는다.
